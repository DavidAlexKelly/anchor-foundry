# Anchor — Roadmap: building out the six pillars

_Companion to `STATUS.md` (what's built, in detail). This document is the build plan for reaching partial Palantir Foundry parity, organised around the platform's six core pillars — Connections, Datasets, Models, Objects, Canvas, Code — each in the detail needed to actually start building, not just a bullet list. Re-read `STATUS.md`'s "What's done" sections before starting any item here; several of these build directly on existing services/migrations named below._

_Completed items are struck through and point at the `STATUS.md` section covering them, rather than being deleted — the reasoning for why an item was sequenced where it was is worth keeping next to what it turned into. **Done so far: Connections 1–3, 5, 6, 7; Datasets 1–3, 5, 6; Models 1–3, 5, 7; Objects 1–3.**_

_What is left in Connections is deliberately not startable rather than merely unstarted: **4** (cloud warehouse) says to pick Snowflake or BigQuery based on what a real prospect names first, and no such conversation has happened; **8** (write-back) wants a design note before code; **9** (streaming) is a flagged stretch. That pillar is done to the point where the next move is a decision, not an implementation. **Datasets** items 1–3, 5 and 6 are done; only 7 (export to a connection) remains besides item 4, and it waits on Connections 8. **Models** items 1–3, 5 and 7 are done: triggers, the graph, the gate against bad *values*, definition history, and cycle refusal. Only item 4 (incremental builds) is substantially left; 6 is largely moot now that item 1 exists. **All three of these pillars have reached the same point**: what remains in each is a decision nobody has made, a dependency on one of those decisions, or an item deferred by the owner. **Objects** items 1–3 are done — the cutover, the Explorer it paid off, and link traversal, which turned out to need a data-model decision (links are derived by joining on property values, not stored as edge rows) before any UI could exist. What remains there is ordinary feature work rather than a structural gap; item 5 (ontology change history) is the next one worth doing, for the same reason Models item 5 was._

## Why this order

Data flows downstream through this platform in one direction, and each pillar's build-out leans on the one before it actually working: **Connections** bring data in → **Datasets** store and version it → **Models** transform it → **Objects** give it a queryable, typed shape (the Ontology) → **Canvas** builds applications and dashboards on top of that ontology → **Code** is an alternate, version-controlled way of *authoring* the Models/Objects layers, so it comes last both because it has the least existing scaffolding (it's the one pillar not started at all) and because "version-control the pipeline" is only worth building once there's a real pipeline shape to version-control.

Within each pillar, items are listed near-term-first; later items in a section usually depend on earlier ones in the same section.

## 1. Connections

**Current state** (`STATUS.md` §6, §14, §21–§24): four connector types (PostgreSQL, MySQL/MariaDB, S3/object storage, generic REST — test, schema discovery, full-snapshot and cursor-incremental sync), credentials exclusively in Secrets Manager, cron or manual scheduling, per-connection error isolation in the worker, schema-drift detection and sync health on top.

A platform whose whole pitch is "connect your data" isn't credible to a real prospect on one source type. This pillar's build-out is mostly about breadth and resilience, not new concepts — the sync/credential/scheduling architecture already generalises, it just hasn't been asked to yet.

1. ~~**Generalise the connector registry before adding the second type.**~~ **Done — `STATUS.md` §21.** The interface is `validate_config`/`test`/`discover`/`snapshot`/`max_cursor_value` behind a `SourceConnector` Protocol, with the registry dispatching on `source_type`. Two shape notes for whoever adds the third connector: `snapshot()` and `incremental(cursor)` landed as one method (an incremental pull is the same extract plus a cursor predicate), and the byte cap is a caller-supplied parameter rather than a connector constant. The worker carries its own trimmed mirror of the extract half — see the standing note in `STATUS.md`'s rough edges about keeping the two registries in step.
2. ~~**MySQL/MariaDB connector.**~~ **Done — `STATUS.md` §21.** PyMySQL, tested end to end against a real MariaDB. It did its job as the abstraction's proof: it forced schema-vs-database vocabulary, per-dialect identifier rules, client-side CSV streaming (no server-side COPY), and code-keyed error translation to move into the connector rather than being assumed platform-wide. It also surfaced that `ssl_mode: required` needed real post-connect verification, since PyMySQL will silently finish a handshake in plaintext.
3. ~~**Object-storage file connector (S3/compatible).**~~ **Done — `STATUS.md` §22.** Bucket + prefix, discovery lists matching files with columns inferred through the datasets layer's own DuckDB readers, one object syncs as one dataset, and "incremental" means the object was rewritten (its `LastModified` is the cursor) since an object store has no row-level cursor. The roadmap's estimate that this was "a smaller lift than a new database driver" held for the ingest half but not the interface: being the first non-relational source, it forced `snapshot()` to return a file *plus its format* rather than always CSV — a Parquet object routed through CSV would discard the types it already carries. Unioning a whole prefix into one dataset is the natural follow-up and was deliberately left out; it needs a rule for what happens when two files under a prefix disagree on schema, which is a design question rather than an extra loop.
4. **A cloud warehouse connector** (Snowflake or BigQuery — pick whichever a real prospect conversation actually names first; don't build both speculatively). Same relational shape as Postgres/MySQL again, but credential handling differs (key-pair auth for Snowflake, service-account JSON for BigQuery) — first connector to exercise a non-password credential shape in Secrets Manager.
5. ~~**Generic REST/API connector.**~~ **Done — `STATUS.md` §24.** Scoped narrowly as this item asked: GET only, a dotted `records_path` to the array, two pagination styles (page number and echoed cursor), and all three named auth schemes. What it does *not* do is written into the connector so the boundary is visible — no Link-header pagination, no XML, no writes, and no server-side incrementality (there is no universal "changed since" for REST, so every run fetches the collection and incremental mode merges by primary key rather than saving bandwidth). Records land as JSONL, not CSV, so nested objects survive.
6. ~~**Schema drift detection.**~~ **Done — `STATUS.md` §23.** `sync_runs.schema_changes` (migration 0018), written by both the API's inline sync and the worker's scheduled job. One deviation from the plan above, with reasons recorded in the migration: the comparison is against the *previous dataset version's* schema, not a setup-time baseline — nothing records a schema at setup today, adding it would mean a discovery round trip per sync (for object storage, listing and downloading files just to read headers), and a stored baseline goes stale the moment anyone edits the connection. The trade is that drift is reported one sync after it happens and reflects what landed rather than what the source declares.
7. ~~**Sync health surfaced in the product.**~~ **Done — `STATUS.md` §23.** A `GET .../connections/sync-health` aggregate (one request for the whole page, not one per row) feeding a "Sync health" column — last result and when, success rate over the last 20 runs, last duration and row count, next scheduled run, and a drift badge — plus a per-connection History dialog with the full run list and expandable schema-change detail.
8. **Write-back connector (PostgreSQL first).** Actions today (§12) write back only to this platform's own dataset copy. Extend the PostgreSQL connector specifically to support a write path (an explicit opt-in per connection, scoped to specific tables/columns, audited the same way `action_runs` already is) — this is real new scope (conflict resolution: what happens if the source row changed since the last sync; permissions: who can enable write-back on a connection at all) and deserves its own design note before implementation starts, not just an extra method on the connector interface.
9. **Streaming sources (Kafka/Kinesis)** — explicitly a stretch item, likely not worth building until a real customer conversation names a concrete streaming need; the existing batch sync (full-snapshot + cursor-incremental) covers the overwhelming majority of "connect a data source" requests a Foundry-shaped product actually gets.

## 2. Datasets

**Current state** (`STATUS.md` §7, §25, §26): upload (CSV/TSV/Parquet/JSON/JSONL → canonical Parquet via DuckDB), preview, column profiling, data-quality expectations with a health badge, sandboxed arbitrary SQL query, export (CSV/Parquet), linear versioning.

The storage/versioning core is solid; what's missing is everything Foundry users actually mean by "Data Health" and richer lineage — the observability and trust layer on top of a dataset, not the storage mechanics themselves.

1. ~~**Column-level profiling in preview.**~~ **Done — `STATUS.md` §25.** `dataset_versions.column_profile` (migration 0019) plus a `Columns` tab beside the row grid. One deviation, argued in the migration: computed *lazily on first request* rather than at version-creation time. That still satisfies "once per version and cached" — a version's data is immutable, so the answer is valid forever and never needs invalidating — while avoiding an aggregate pass on every path that creates a version (upload, both sync paths, both model paths, action write-back) to produce something nobody may look at.
2. ~~**Data quality / expectations.**~~ **Done — `STATUS.md` §26.** All five rule types, per-column, with `error`/`warn` severity, and a pass/warn/fail/none health badge. One deviation, argued at length in migration 0020: results are computed **on demand and cached**, not at version-creation time. The seven creation paths across two codebases are a large blast radius, and — the real reason — a result computed at creation is stale the moment somebody edits the rules, which is exactly when a health badge most needs to be right. Any rule change invalidates the cache, and one read path computes-if-absent, so every creation path stays untouched and correct. The one thing this cannot do is alert at the moment a bad version lands (no reader to trigger the computation); that would need genuine eager evaluation and is flagged in the migration. Models' build-gating item can now read `GET .../datasets/{id}/health`.
3. ~~**Schema enforcement policy per dataset.**~~ **Done — `STATUS.md` §31.** `datasets.schema_policy` (migration 0023), `permissive` by default for the same reason 0022's gate defaults to `ignore`. One deliberate narrowing of "must match the previous version's schema": **adding a column is allowed under strict**. Taking it literally would reject the most common and most harmless drift there is, and a policy people keep switching off is one nobody leaves on — what breaks a downstream reader is a column going away or changing type. This item's recommendation that strict be the *default* for anything with a downstream dependency is deliberately not implemented: nothing should silently start failing pipelines on migration day, and "has a downstream model" is a property that changes without the dataset's owner doing anything. Enforced in a **trigger**, which is a reversal of migration 0021's argument against database logic and is argued at length in 0023 — the deciding factor is that seven writers across two codebases insert versions, so an application-layer check holds only until somebody forgets.
4. **Wire the Athena path that's already promised in code.** Upload/sync/model size caps (50MB/200MB/5M rows) are commented in code as "the point where the Athena/worker path takes over," but nothing calls Athena anywhere despite `workerTaskRole` already holding the IAM permissions for it (`infra/cdk/src/constructs/services.ts`). Either build the large-dataset path for real (a worker job that runs the same transform via Athena against data staged in S3, for datasets over the interactive cap) or remove the promise from the comments and the unused IAM grant — don't leave a customer's oversized upload hitting an opaque rejection with no real path forward.
5. ~~**Interactive lineage graph.**~~ **Done — `STATUS.md` §33.** The item said to reuse "whatever graph-rendering approach Models item 2 settles on"; reusing the same **endpoint** turned out to be the stronger version of that — `GET .../pipeline?focus=dataset:<id>` returns the node's connected component, laid out by the same code, and one React component renders both views. It also turned out this was as much "surface lineage at all" as "make it interactive": the Mermaid endpoint existed, was tested, and **nothing in the frontend had ever called it**. The component walk is deliberately *undirected* — a dataset's lineage is what produced it and what reads it, including a sibling model on the same input, which is what someone tracing an outage needs. The Mermaid endpoint stays for the spec's "exportable as JSON or Mermaid".
6. ~~**Dataset forking (lightweight branching).**~~ **Done — `STATUS.md` §34.** Exactly the small version this item scoped: `POST .../datasets/{id}/fork` copies one version into a new dataset with `origin='fork'` and provenance columns (migration 0025). Nothing here knows how to merge a fork back, on purpose — deciding what a merge means for tabular data is the large lift the item warns about, and it stays unbuilt until real usage shows forking is not enough. Three decisions worth carrying forward: the **bytes are copied, not shared** (sharing a storage key would make deleting the original silently empty the fork); the **quality rules travel but their results do not** (forking is for testing a change against the same standard, but a result is per-version and the fork's v1 is new); and a fork **starts permissive** whatever the source's schema policy was, since inheriting strict would make the thing you forked in order to experiment with refuse the experiment. It also got more useful than it looked when written: items 2 and 3 plus Models 3 are all things you want on in production, and all of them mean you now need somewhere else to try the change that would trip them.
7. **Export to a connection**, symmetric with Connections item 8's write-back — once a connection can accept writes, "export this dataset back to source" becomes a natural Datasets-side feature reusing the same path.

## 3. Models

**Current state** (`STATUS.md` §9, §14): SQL (DuckDB sandbox, synchronous) and Python (subprocess sandbox, worker-queued) transforms, manual/cron scheduling, run history, per-model lineage.

Foundry's Pipeline Builder is essentially this layer plus a real DAG view, real incremental builds, and quality gates — the conceptual pieces (models, datasets, versions, runs) already all exist here.

1. ~~**Upstream trigger mode.**~~ **Done — `STATUS.md` §27.** Exactly the pattern this item asked for: `list_due_upstream_models()` (migration 0021) discovers across workspaces, the worker re-verifies through a scoped connection, and due-ness is "an input dataset gained a version since `models.upstream_watermark`" rather than a cron tick. Two things the item didn't anticipate, both argued in the migration: a **self-loop guard** is required — a model whose output is also one of its inputs would otherwise re-trigger forever — and the **two-model cycle** (A→B→A) is documented rather than solved, because detecting it needs the whole graph, not one model's inputs, so it belongs with item 2. Chains settle one poll pass per link, which is a property of polling, not a bug; resolving a chain in a single pass needs topological order, again item 2's graph.
2. ~~**A real pipeline DAG view.**~~ **Done — `STATUS.md` §28.** A project-level `Pipeline` page: every dataset and model as one graph, last-run status and health on each node, pan/zoom, click a node for its detail and a jump to its own page. The item said to "build it on the same graph-rendering choice as Datasets item 5" — that choice turned out to be **no library at all**. The API returns each node's layer and position (`GET .../pipeline`, `services/pipeline.py`), so drawing it is arithmetic plus SVG beziers; that keeps the layering testable in pytest against real rows rather than only in a browser, and Datasets item 5 can reuse the same endpoint's shape for a single-node view. It also picked up the **cycle detection** that migration 0021 deferred here: cycles are grouped, reported, and drawn in the danger colour with a banner naming the consequence. Detecting a cycle is not preventing one — refusing to *save* an edge that closes a loop is a separate decision about model edits and is item 7 below.
3. ~~**Data quality gating.**~~ **Done — `STATUS.md` §29.** `models.input_health_policy` (migration 0022) with the three modes this item implies plus one it didn't name: `ignore` (the default, deliberately — applying a migration must not silently start failing models that ran fine yesterday), `warn` (run and record what was wrong), and `block` (refuse). `warn` earned its place: it is the mode you turn on to learn how often blocking *would* have fired, before committing to it. The gate holds on both the interactive API path and every automated one, which required mirroring the expectations evaluator into the worker — a gate that only held where a human was watching would be the same do-nothing promise item 1 existed to remove. It also, incidentally, supplies the "reader" migration 0020 said expectations were missing: the gate computes health when nothing has cached it, so `block` is enforced against data nobody has opened.
4. **Incremental model builds.** Today a model run appears to fully recompute from its inputs' current state every time. For SQL models over a connection-backed dataset that's itself grown large, add an incremental mode mirroring Connections' cursor-incremental sync (process only rows new since the last successful run, keyed on a declared cursor column) — matters for real performance parity once datasets aren't toy-sized.
5. ~~**Model version history / rollback.**~~ **Done — `STATUS.md` §32.** `model_versions` (migration 0024), same append-only shape as dataset versioning, backfilled so every existing model starts at v1. Three decisions the item didn't specify. **Rollback appends rather than rewinds**: restoring v2 writes a new v5 with v2's content, so history stays a true record and `model_runs.model_version` never becomes ambiguous. **A version snapshots the code *and* the inputs**, because aliases are half the contract — restoring `FROM orders` into a model whose input was renamed restores something that cannot run. **Trigger mode, schedule, health policy, name and description are not definition changes**: they are how and when a model runs, not what it computes, and versioning them would fill the history with entries nobody would roll back to. It also closes the asymmetry that motivated the item: `model_runs.output_version` has always pointed at the exact data a run produced, and `model_version` now points at the exact code. A side-by-side diff view is deliberately not built — the versions are stored, so it can be added later without a schema change.
6. **Dependency-aware scheduling.** Once item 1 (upstream triggers) exists for the common case, this becomes mostly moot for chained pipelines — but independent cron-scheduled models with an implicit ordering expectation (B should run sometime after A's daily sync, but isn't literally fed by A) still race today. Lower priority than items 1–5; revisit once upstream triggering is live and it's clear whether this gap still matters in practice. **Now revisitable:** item 1 is live, and the gap it leaves is narrower than written here — a model that is genuinely fed by another needs no scheduling at all now, so what remains is only the implicit-ordering case, plus the one-pass-per-link settling time, which is a latency question rather than a correctness one.
7. ~~**Refuse to save a model edit that closes a cycle.**~~ **Done — `STATUS.md` §30.** In `_validate_and_set_inputs` as this item proposed, via a recursive walk over every dataset downstream of the model's own output. Existing cycles are **grandfathered**, which is the question this item left open: the check validates the *proposed* input set, so a pre-existing loop keeps working until somebody edits one of its models, at which point the edit is refused until they break it. Force-breaking on next edit would mean silently deleting an input someone configured on purpose — the Pipeline page names the loop instead, which is a better place to be told.

## 4. Objects (Ontology)

**Current state** (`STATUS.md` §10, §11, §12, §14, §35): object types + typed properties + link types (workspace-scoped), dataset→type mappings with sync (project-scoped), an instance store behind a Protocol with Postgres and OpenSearch implementations and a backfill between them (§35), Actions for write-back to the platform's own dataset copy.

The structural gap that used to head this section is closed, item 2 has cashed it in, and item 3 has made the ontology *connected* rather than merely typed. What is left is items 4–6, and they are ordinary feature work rather than gaps in the layer: richer property types, a change trail on type definitions, and actions that write to more than one instance. Item 5 is the one with a real failure mode behind it (a consumer silently breaking when a property disappears), so it is the next one worth doing.

1. ~~**Cut the instance store over to OpenSearch.**~~ **Done — `STATUS.md` §35.** All four things this item asked for, plus two it could not have known about. The seam is `PostgresInstanceStore` implementing the *same* Protocol as the OpenSearch one, so the Postgres path stays as the fallback and local-dev default instead of being deleted at cutover; `backfill()` is the migration step, and it is **idempotent**, which is what let the dual-write period be replaced by a simpler procedure (**backfill, flip, backfill again**) rather than machinery that fails quietly when one of two writes does. Every existing objects/actions test passes through the seam unchanged, and the whole instance API is additionally tested end to end *on* the OpenSearch store. The two surprises: `action_runs.instance_id` had a foreign key into `object_instances`, which is unsatisfiable once instances live elsewhere (migration 0026 drops it), and **`opensearch-py` alone does not provide `AsyncOpenSearch`** — it needs the `[async]` extra, so the gateway §14 shipped would have raised ImportError the first time a deployment used it. Remaining honestly unverified: no real cluster. The gateway is tested over real HTTP against a fixture implementing the REST subset it uses, which proves its requests and parsing, not that OpenSearch agrees.
2. ~~**Global Ontology / Object Explorer.**~~ **Done — `STATUS.md` §36.** `GET .../object-instances?q=&type_id=` searches every instance in a workspace at once, and the objects page gains an Explore panel over it: one table, one row per instance, each labelled with the type it is, with a union of the properties present so a cross-type result still shows values rather than ids. Two things worth carrying: it is **workspace-scoped, not project-scoped**, because object types are — an explorer that stopped at a project boundary would show a partial ontology and call it the whole one; and `search()` is on the *Protocol*, so the Postgres store implements it too, honestly, as `ILIKE` over the properties JSON. That is substring matching, not search — no tokenisation, no relevance — which is exactly why this item was sequenced after the cutover, and it is written into `services/instances.py` rather than left to be discovered.
3. ~~**Relationship/link traversal UI.**~~ **Done — `STATUS.md` §37.** The item described a UI, and the UI is there — an Explore panel on any instance, one section per link, with click-through and a breadcrumb trail. But it was **not a UI item**: `link_types` recorded only *which types* relate, and `grep` found no link-instance table anywhere in twenty-six migrations, so there were no edges between instances to browse. The decision that had to be made first was where instance-level links come from, and the answer is **derived, not stored**: migration 0027 adds `from_property`/`to_property` to `link_types` and a traversal joins on those values. Instances are themselves *materialised* from dataset mappings and re-materialised on every sync, and the relationship already arrives in that data as a foreign key column — storing edge rows would have meant a second sync mechanism going stale beside the one that produces the rows its edges point at. Two things the item did not anticipate: `'$primary_key'` had to be a reserved join reference, because the far end of a foreign key is nearly always the referenced row's key and the primary key is a field on an instance rather than one of its properties; and the join needed an **exact-equality** store operation, because the only lookup that existed was the Explorer's `phrase_prefix` search, which would have answered "who works in ENG" with the people in "ENG West" and no visible sign of the error.
4. **Richer property types.** Today's typed properties are presumably basic scalars — add geopoint (unlocks a Canvas map widget, item 3 in that section), timestamp-with-timezone if not already distinct from a plain string, and a media/attachment-reference type (pointing at a file in the existing S3 storage gateway, not a new storage mechanism).
5. **Ontology change history.** Changing an object type (adding/removing/retyping a property) has no audit/version trail today — a consumer (a Model, a Canvas app, a mapped dataset) relying on a property that gets silently removed just breaks. Add versioning on object-type definitions, surfaced as a warning when a change would affect an existing mapping/action/model, mirroring Models item 5's rationale for the same problem one layer up.
6. **Richer Actions.** Today's actions write back to exactly one instance. Bulk/multi-object actions (apply the same write across a filtered set of instances) and action side-effect chaining (an action that also, say, triggers a model run) are natural extensions of the existing `action_types`/`action_runs` shape — scope as a follow-up once single-instance actions have real production usage to learn from, not before.

## 5. Canvas

**Current state** (`STATUS.md` §15): Craft.js-based visual editor, four widgets (Container, Text, Dataset table, Action form), publish visibility (private/workspace/groups).

The "BI" half of "app/BI builder" is the explicit, named gap here (STATUS.md's own words) — this pillar's build-out is mostly about closing that.

1. **Parameter/filter widgets.** Before charts are useful, cross-widget interactivity needs a mechanism: a dropdown/date-range/search-box widget that other widgets can subscribe to (via the existing `CanvasEnvProvider` context, extended to carry shared parameter state alongside workspace/project id and edit-mode). Build this first — chart widgets and cross-widget interactivity both depend on it existing.
2. **Chart/BI widgets.** Bar/line/scatter/pie at minimum, bound to a dataset (reusing the existing preview/query endpoint for the underlying data, aggregated client-side for small results or via a new lightweight aggregation endpoint for larger ones) and reactive to item 1's filter widgets. This is the single most-requested-sounding gap in the whole roadmap given the "BI" framing — prioritise it right after the filter-widget foundation.
3. **An Ontology Object browser widget.** A live, filterable table bound directly to an object type (via item 4's Global Object Explorer work), not just a raw dataset — this is a more Foundry-native pattern than the dataset-table widget alone, since real Workshop-style apps are built on ontology objects far more than on raw datasets. Sequence after Objects item 2 (Global Ontology view) exists to reuse its query surface.
4. **Map widget**, once Objects item 4 (geopoint property type) exists — bind to any object type/dataset carrying a geopoint column, render pins/clusters.
5. **Cross-widget interactivity beyond filters** — e.g. a table row selection driving another widget's detail view — same resolver/widget extension pattern as the rest of this pillar, lower priority than items 1–4 since parameter widgets (item 1) already cover the most common real use case.
6. **Drag-and-drop reordering of placed widgets**, published-apps nav page (the read API already exists, §15/§not-started — just needs a list page and a nav entry) — smaller, standalone polish items, fine to slot in whenever convenient rather than needing to wait on anything above.
7. **Embedding/sharing outside the platform** (a public or token-scoped share link) — explicitly a stretch item; bigger scope (auth model for an unauthenticated or token-authenticated viewer) than anything else in this section, revisit once the widget set itself is actually competitive.

## 6. Code

**Current state**: not started at all — the one pillar with zero existing scaffolding.

Foundry's real Code Repositories are git-backed and tightly coupled to the pipeline layer (checked-in transform code building datasets via CI, with review-gated promotion). Because nothing exists yet and this platform's whole premise is running entirely inside the customer's own AWS account (not phoning home to an external git host), this pillar needs a short design spike *before* implementation — unlike the other five sections, don't start writing code for item 2+ until item 1 is actually decided.

1. **Design spike: where does the git data live?** The core open question is whether to build a lightweight self-hosted git backend (e.g. `dulwich` or the real `git` binary operating against a repo directory backed by EFS or S3, running inside the customer's own VPC — consistent with "runs entirely inside the customer's account") versus federating with the customer's own external GitHub/GitLab (much less backend work, but couples a from-the-customer's-account-outward dependency into a platform whose entire pitch is self-contained deployment, and raises the question of where credentials for that external service live). Write this up as a short decision doc before touching code — it changes the shape of everything below.
2. **Scope narrowly: transform code first, not a general IDE.** The first cut should be a git-backed store for Model definitions specifically (the SQL/Python source Models already has, §9/§14) with real commit history — not a general-purpose repository browser for arbitrary files. This keeps the surface small enough to actually ship, and gives Code a clear, immediate connection to a pillar that already works.
3. **Round-trip with Models.** Editing a Model's code through Code should trigger the same build path (`model_runs`/`dataset_versions`) the existing inline editor already produces — Code becomes an alternate, version-controlled *authoring surface* for the same underlying pipeline concept from Models item 5, not a parallel, disconnected system. This also means Models item 5 (definition versioning) and Code's commit history may end up being the same mechanism viewed two ways — worth explicitly reconciling during item 1's design spike rather than building both independently and merging later.
4. **Review-gated promotion.** A PR-like review step before a change to a transform's code takes effect on whichever branch/environment is considered "live," mirroring Foundry's actual review-gated pipeline model. This is meaningfully large scope on its own (review UI, approval state, branch-to-environment mapping) — sequence last within this pillar, once items 1–3 are proven with real usage.
