# Data Connection — parity specification

**Source:** `docs/pal/foundry_data-connection.pdf`, 417 pages — the largest doc in the set.

**Today:** `apps/api/src/services/connectors.py` with Postgres, MySQL/MariaDB, S3 and REST connectors behind a `SourceConnector` interface (§2–§7); sync runs with schema drift detection (§5) and sync health (§6).

**Read this one differently.** 417 pages is misleading: most of it is per-connector setup guides and agent configuration reference, and much of the rest describes infrastructure we deliberately do not have (customer-hosted agents, Rubix egress policies, streaming). **Parity here means parity with the model, not with the connector catalogue.** A connector we do not have is a day's work against an interface that exists; a concept we have not modelled is a migration.

This is stage 6 — lowest felt urgency, because it is plumbing users rarely see.

## 1. The core model (p.10–12)

| Concept | Foundry | Ours |
|---|---|---|
| **Source** | "a single connection to an external system, including any configuration necessary to specify and locate the target system (typically a URL) and the credentials required to successfully authenticate" | ✅ connections |
| **Connector** (source type) | the kind of system; determines available capabilities | ✅ |
| **Credential** | "a secret value required to access a particular system… all credentials are encrypted and stored securely" | ✅ `secrets.py` |
| Credential-free auth — OpenID Connect, outbound applications, cloud identity | (p.11, p.359, p.391) | ◑ §599 — **cloud identity** is S3's platform role, as before: a source with no key uses the platform's own credential chain. **§599 built p.391's OpenID Connect**: "Foundry acts as the OIDC identity provider; every time a workflow in Foundry is required to authenticate with the source system … Foundry will issue an OIDC token with claims that identify the Data Connection source being used." The platform publishes a discovery document and key set at `{issuer}/.well-known/openid-configuration` and `{issuer}/jwks`. Both are public, as a source system fetching them has no user, and both are 404 when the deployment has not set the platform up. The deployment sets `OIDC_ISSUER` (its public address) and an RSA `OIDC_SIGNING_KEY`, since every API task and worker must sign with the key the published set holds; `dev-up.sh` generates a local one once. A token is p.391's example: `iss`, `sub` (`connection.<resource id>`, stable across a rename, and what p.391 says to filter on), `aud`, `iat`, `nbf`, `exp` an hour later, and `jti`; RS256 with the key's RFC 7638 thumbprint as `kid`. It is signed by hand with `cryptography`, so the worker holds a verbatim copy, and a test holds the two together. **S3 is the one of p.391's six sources this platform has**: a role ARN and an audience (`sts.amazonaws.com` by default) make the source trade a token at AssumeRoleWithWebIdentity for an hour's credentials. That happens at AWS, or at an S3-compatible store's own endpoint, which is where MinIO answers it. The token is minted when the connector connects, on every path: test, browse, sync now, a scheduled sync, and exports interactive or scheduled. So a deployment that cannot sign is an ordinary connector failure on the path that met it, and no other. Such a source stores no key: one sent with it is refused, and a keyed source moved to OIDC forgets its key. A deployment with no issuer refuses the source when it is saved rather than at its first sync. The connection list shows what the role's trust policy has to name (issuer, audience, subject). A refused token names the three to check. Tested against moto's STS end to end, the token checked against the published key set as a source system would. Sweep 29/29. ○ for **outbound applications** (an OAuth application registered with the source system), and for p.391's other five sources, which are not connectors here. |
| **Worker** | where compute for capabilities runs | ○ — implicit; ours always runs in our worker |
| **Networking / egress policies** | how target systems are reached | ✅ §263 the rule, the store and all four outbound paths; §264 the panel. ○ for agent proxy policies and host overrides (decision 0013 §1), and for **protocol** as part of a destination (p.37, decision 0013 §5) |

Foundry separates **worker** (where compute runs) from **networking** (how the target is reached), and says so explicitly because customers get it confused. We have neither concept — everything runs in our worker and reaches out directly.

**Recommendation: do not model workers.** Agent workers are legacy in Foundry's own words ("Agent worker is in the legacy phase of development. We recommend migrating existing agent worker sources to Foundry worker", p.12), and customer-hosted agents are a support burden we should not take on. **Do model egress policies** — an explicit allowlist of destinations per source is a security control we will be asked for.

A **concurrency limit** (1–100 at once) and a **rate limit** (1–1,000,000 per second, minute, hour or day, as calendar windows in UTC) are both off unless set, as p.240 sets neither. Both are counted in the database by one function that locks the webhook's row, on a connection of its own, so they hold across API tasks and are committed before the call starts. A running execution holds a slot until it finishes, or until 30 seconds past its timeout if its API task dies. A refused execution is a failure with no status (p.237: nothing changed), so a writeback refuses its action and a side effect is recorded and passed over. A webhook may make up to nine calls before its own request, in order. Each has a method, a path and a JSON body, and names the values it **extracts** from its response by dotted path ("." is p.235's whole-response extract). A later call and the request reference them as `{{{name}}}`, typed when a whole value; a call may not reference its own or a later call's. **p.237's rule is enforced on save:** "only one call is allowed to use an unsafe HTTP method", with a call marked *only reads* (p.237's `isHttpMethodSafe`) not counting. A failing call stops the chain, is named ("call 2: …"), and answers p.237's question from the whole chain: a failure after a call that changed the far end reports the change as landed, a failing read reports nothing changed, and otherwise the status decides. **p.240's time limit covers the whole chain**, each call getting what is left of it. | **Listeners** — inbound events | TOC §30–39 | ◑ §516, §517, §518, §519, §520, §521, §591, §593 — **HTTPS listeners** (p.249-266; db 0106). p.249: listeners "provision a URL endpoint, implement the specific message signing or other verification schemes … and allow a simple and low-latency mechanism to receive data feeds". A listener has a random endpoint address, and `POST /api/listen/{token}` takes a request with **no user**: an outside sender can do exactly two things, through db 0106's two SECURITY DEFINER functions. It can find the listener its token names and append one event. A new listener is **stopped** until started, so it takes no traffic before it is configured. p.265's generic schemes are none, basic authentication, a secret in a named header, and an HMAC-SHA256 signature of the body (hex, with or without `sha256=`), all compared in constant time. The secret goes to the secrets store (`services/secrets.py`) and is never returned. p.262's **1 MB** limit refuses a larger body either way it arrives. The request is read one byte past the limit rather than held whole. p.261's **stream** is `listener_events`, newest first on the listener's card, with a text preview; the headers are kept with p.265's redactions (Authorization, cookies and the listener's own secret header). **§517 built p.258-259's endpoint rotation.** Rotate makes a new active endpoint, and either keeps the old one answering until an expiry ("You should now have two usable endpoints") or deletes it at once. A listener has at most two endpoints and one active, so a third is refused until the retiring one is deleted. A retiring endpoint can be extended by a day, but not once it has expired ("you can no longer modify the expiration date"). Only a non-active endpoint can be deleted, since deleting the active one would leave no address. The card lists each endpoint with its state and time left. **§518 built p.262's named listeners** (db 0107): Slack, Jira, GitHub, GitLab, Stripe, Shopify and Google Cloud Pub/Sub. Each is a preset that fixes the scheme and the header, so its author gives only the secret (p.285: "enter the Signing Secret value"). Four schemes came with them. **Slack's** HMAC over `v0:{timestamp}:{body}` and **Stripe's** over `{t}.{body}` both refuse a timestamp more than five minutes off, so a captured request cannot be replayed; Stripe accepts any `v1` while a secret is rolled. **Shopify's** HMAC is in base64. **Pub/Sub's** token rides in the address (p.274: "?token=<YOUR_TOKEN>"). Jira may sign or not (p.279). Slack's set-up handshake (p.287) is answered with its challenge when signed, and is not kept as an event. The browser's list of types is checked against the server's by a test that reads it. **§519 built p.264's archive** (db 0108): "Every few minutes, the listener event stream will archive into a backing dataset". The worker's `archive_listener_events` runs every five minutes, and **Archive now** on the card runs the same thing. The two archivers share one block of code (the columns, the batch ceiling, the query and the Parquet writer), held to the same text by a test. Each run appends the events after `archived_through` to a new version holding everything so far, up to 5,000 events or about 50 MB; the first event is always taken, so one large event cannot stall the archive. The dataset is an ordinary one, origin `listener`, named after the listener, with a number when the name is taken. §506's **Made by** names the listener. Deleting the dataset starts the archive over from the first event. The card says where events go and how many are waiting. **§520 built p.254-255's ingress allowlist** (db 0109), per listener rather than per subdomain. Palantir's subdomain exists to carry its own network-ingress configuration; this platform has no per-hostname ingress, so the allowlist goes on the listener itself. An empty list is p.255's **inherited ingress**: any sender the platform accepts. A non-empty list is **custom ingress** (p.254: "Configuring a small IP range … to allow requests to a listener with only basic authorization or header secret verification available"). Up to 50 IPv4 or IPv6 ranges are allowed; they are normalised (`10.1.2.3/8` becomes `10.0.0.0/8`, a bare address becomes a /32) and deduplicated. A sender outside the list is refused with 403 before anything else about the listener is said, even that it is stopped. **The sender is the address the nearest trusted proxy vouched for**: `LISTENER_PROXY_HOPS` (1 behind the ALB, set in the CDK services construct) picks that entry of X-Forwarded-For counted from the right. Entries to its left came from the sender and prove nothing, which is why uvicorn's `forwarded-allow-ips` (which takes the leftmost) is not used. An IPv4 address written as IPv6 is read as IPv4. The card says who may send, and gives editors a one-range-per-line editor. **§521 built p.261's rate limit** (db 0110): "rate-limited at approximately 100 requests per second". The limit is per listener and counted in the database, so it holds across API tasks. The count is one row per listener: a fixed one-second window, which is the "approximately" (a burst straddling two seconds can take up to twice the limit). Every request that reaches a running listener counts, including one that then fails verification or is too big, so a sender that cannot sign cannot send without limit. Requests refused before that (unknown address, outside the allowlist, stopped) are not counted, so a sender outside the allowlist cannot use up the budget of those inside it. The count commits in a transaction of its own before the request is judged. Over the limit, the request gets 429 with `Retry-After: 1` and is not an event. The card says how many requests were refused and when (p.261's remedy is asking for more), and the panel states both limits, held to the server's by a test. **§591 added seven more of p.262's table** (db 0124): Bitbucket, Meta, Azure Event Grid, Jotform, PagerDuty, Zendesk and Airtable, each with the scheme its sender documents (p.265: "the security protocols laid out by those external systems"). Bitbucket (`X-Hub-Signature`) and Meta (`X-Hub-Signature-256`) sign as GitHub does. Event Grid sends a shared key in `aeg-sas-key`. Jotform signs nothing, so it takes a token in its address or nothing, as Jira may. Three schemes came with them. **PagerDuty's** `v1=<hex>` HMAC of the body takes any of the listed signatures, one per secret while a secret is rolled. **Zendesk's** base64 HMAC is over `{timestamp}{body}`, the timestamp in ISO 8601 beside it; a stale one, or one with no zone, is refused. **Airtable's** `hmac-sha256=<hex>` is keyed with the bytes its base64 MAC secret encodes, so a secret that is not strict base64 is refused when set (and by the form before that). Not built for these: Meta's and Event Grid's subscription handshakes, which ask a GET or a validation event to be answered, where the author confirms the subscription on the sender's side instead. **§593 added five whose proof is not a header of their own** (db 0125). **Cisco Meraki** sends the shared secret inside its payload (`sharedSecret`), which is kept redacted, as p.265 redacts a secret header. **PandaDoc** adds `?signature=`, a hex HMAC-SHA256 of the body. **Dialpad**, given a secret, sends each event as an HS256 token (only HS256: a token naming another algorithm is refused rather than trusted to say how to check it, and an expired one is refused); the event kept is the JSON inside it, as Dialpad sends it without a secret, which it may (`none`). **Twilio** signs the address it posts to: base64 HMAC-SHA1 of the URL, then each form parameter's name and value sorted, or for a JSON body the URL's `bodySHA256`, which must be the body's hash. The server checks the address as it sees it, which is the one the card shows, and a browser test holds the two together through the web tier. **Twilio SendGrid** signs `{timestamp}{body}` with ECDSA, checked with the public key SendGrid gives (refused when set if it is not an elliptic-curve public key, PEM armour read past), and a stale timestamp is refused as Slack's is. Sweep 22 of 22, after removing two guards that could not change an answer: an `isinstance` check on what PyJWT returns (it refuses a payload that is not an object), and a refusal of a form that is not UTF-8 (read with replacement characters, it matches no signature Twilio makes). ○ within the row: the other nine of p.262's table. AWS SNS and Microsoft Bot Framework sign with certificates or keys fetched from the sender at request time, so an inbound request would make this server call out, which nothing else here does. For Apollo, FedEx, ION Factory OS, project44, RevelocPlus, ShipStation and Skydio, the linked documentation names no signing scheme this build could hold a test to (RevelocPlus has no link at all), so each is a custom listener until one is published. Also ○ is p.250's **subdomains** as hostnames (with their approval request). WebSocket (experimental) and email (beta) listeners are out of scope. |

## 3. Connector catalogue

Ours: Postgres, MySQL/MariaDB, S3, REST/HTTP.

Foundry ships dozens. Parity with the catalogue is neither achievable nor desirable — "Foundry without the bloat" argues directly against it. What matters is that the **interface** is right, which §2 of the phase-1 roadmap established by proving it with a second database connector.

The honest position: **add connectors on demand, not speculatively.** Each is roughly a day against the existing interface. The gaps most likely to be asked for first, in order: SQL Server, Snowflake, BigQuery, SFTP, Google Cloud Storage, Azure Blob.

Foundry's own fallback is worth copying: "For systems without a dedicated connector, the generic connector or REST API source may be used with code-based connectivity options" (p.10). Our REST connector already is that fallback. Make sure it is documented as such.

So the credential-refusal cases here are the feature rather than its error path, and `test_a_failed_read_does_not_mark_the_connection_broken` is the pair that keeps them from becoming a false alarm. Two things the row above cannot say: **the sample is not the first rows** — there is no `ORDER BY`, because one would need a key the source may not have and would turn the cheapest check in the platform into a full sort, and p.161 already uses the phrase for the equivalent choice on the file side ("a non-deterministic subset"); and **it is a preview of a table, never a query**, because the moment a caller can shape the read, an editor seeing fifty rows becomes an editor running statements as the connection's user. §269's half is the screen, and its own finding is smaller and worth keeping: **most of what the Explore screen does is say what the sample is**. A table of fifty rows with no caption is one somebody reads as the data, so the row count says "all 12 rows" or "50 of more than 50", the non-determinism is stated only where there is a subset to be non-deterministic about, shortened cells are counted, and a null is the word `null` rather than a blank cell the server went to trouble to keep distinct. The search covers **column names** as well as table names — "which table has `customer_email`" is the question people arrive with — and a match a name does not explain says where it came from.
