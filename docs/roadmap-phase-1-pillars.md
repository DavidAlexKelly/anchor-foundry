_Completed items are struck through and point at the `STATUS.md` section covering them, rather than being deleted — the reasoning for why an item was sequenced where it was is worth keeping next to what it turned into. **Done so far: Connections 1–3, 5, 6, 7; Datasets 1–3, 5, 6; Models 1–3, 5, 7; Objects 1–5; Canvas 1–4, 6; Code 1–4; Deployment 1–4 — every item in both.**_

_What is left in Connections is deliberately not startable rather than merely unstarted: **4** (cloud warehouse) says to pick Snowflake or BigQuery based on what a real prospect names first, and no such conversation has happened; **8** (write-back) wants a design note before code; **9** (streaming) is a flagged stretch. That pillar is done to the point where the next move is a decision, not an implementation. **Datasets** items 1–3, 5 and 6 are done; only 7 (export to a connection) remains besides item 4, and it waits on Connections 8. **Models** items 1–3, 5 and 7 are done: triggers, the graph, the gate against bad *values*, definition history, and cycle refusal. Only item 4 (incremental builds) is substantially left; 6 is largely moot now that item 1 exists. **All three of these pillars have reached the same point**: what remains in each is a decision nobody has made, a dependency on one of those decisions, or an item deferred by the owner. **Objects** items 1–5 are done — the cutover, the Explorer it paid off, link traversal, change history, and richer property types. The last three each turned out to need something the item did not mention: link traversal needed a data-model decision (links are derived by joining on property values, not stored as edge rows), change history needed the *edit operation* it was meant to record, and richer types needed three existing enum labels to start meaning anything at all. Only **6** (bulk and chained actions) is left, and the item itself defers it until single-instance actions have real production usage. **Objects has therefore reached the same point as the three pillars above it**: what remains is work the roadmap explicitly wants evidence for first. **Canvas** is where the work is now, and its three highest-value items are done: item 1 (the parameter mechanism the pillar's own sequencing said had to come first), item 2 (chart/BI widgets — the gap this document called the single most-requested-sounding one, given the "app/BI builder" framing) and item 3 (the ontology object browser, which made canvas apps read the ontology rather than only raw datasets). Item 3 repeated the pattern the last three Objects items set: its stated dependency existed, and was still not enough — the Explorer could only *search*, and a filter that quietly behaves like a search is wrong in a way that looks right, so the exact read path had to be built before the widget could be honest. Item 4 (the map) then made the deferred decision it inherited from Objects item 4 — where a basemap comes from — and answered it with "not from anyone else's server", since this product's whole premise is a deployment inside the customer's own account. Item 6 then turned out to be the fourth item running whose stated scope was not the work: it called itself "a list page and a nav entry", and the actual gap was that **publishing had nowhere to lead** — the only route that rendered an app was the project editor, which 404s for exactly the people publishing exists for. **Canvas has now reached the same place as the pillars above it**: item 5 is a design question whose common case parameters already cover, and item 7 is a flagged stretch needing an auth model for viewers outside the platform. That makes **Code**, the one pillar with no scaffolding at all, the next substantial body of work — and its item 1, the design spike everything else there is blocked on, is now decided (`docs/decisions/0001-where-code-lives.md`): no git server, the system of record stays in Postgres, and git federation is an optional outbound mirror to a remote the customer already owns. The reason is one the item could not have known to ask about — a run is pinned to the exact definition that produced it, and a git ref cannot promise that. Items 2 and 3 followed immediately, and the spike made them smaller than the roadmap thought: item 2 is a repository-shaped surface over versions that already exist plus the change set that lets one edit span several transforms, and item 3 needed no work at all — with one store there is no round trip. Item 4 then closed the pillar, and with it the last unbuilt item in this document: proposals, approvals and a per-project gate, all platform-native because an external repository must never be what authorises a change to what runs here. It also declined a third of its own scope — branch-to-environment mapping — since there are no branches or environments to map, and inventing both to satisfy a phrase would be the tail wagging the dog. **What remains anywhere in this roadmap is the deliberately-not-startable set**: decisions nobody has made (Connections 4, 8), items waiting on those decisions (Datasets 7), items the roadmap itself defers pending real usage (Objects 6, Canvas 5), flagged stretches (Connections 9, Canvas 7), and two genuine build items nobody has needed yet — Models 4 (incremental builds) and Datasets 4 (the unwired Athena path). **The work that is startable today is in section 7**: the six pillars are a product nobody can reach until connecting an AWS account stops being a runbook. **Section 7 is now complete too**: the onboarding page and the surface behind it (2), the operator CLI, control-plane image and runbook (1), the first-run checklist (3), and failure recovery (4). What is left anywhere in this document is the not-startable set named above, plus Models 4 and Datasets 4 — and the deploy-pipeline hardening carried forward below, which is the natural next move now that a deployment is something a person can actually do._

## Why this order

Data flows downstream through this platform in one direction, and each pillar's build-out leans on the one before it actually working: **Connections** bring data in → **Datasets** store and version it → **Models** transform it → **Objects** give it a queryable, typed shape (the Ontology) → **Canvas** builds applications and dashboards on top of that ontology → **Code** is an alternate, version-controlled way of *authoring* the Models/Objects layers, so it comes last both because it had the least existing scaffolding (it was the one pillar not started at all) and because "version-control the pipeline" is only worth building once there's a real pipeline shape to version-control. That ordering paid off in the end: by the time Code was built, the pipeline it versions already existed, and the decision about where its data lives fell out of a guarantee Models had already made.

Within each pillar, items are listed near-term-first; later items in a section usually depend on earlier ones in the same section.

## 1. Connections

**Current state** (`STATUS.md` §6, §14, §21–§24): four connector types (PostgreSQL, MySQL/MariaDB, S3/object storage, generic REST — test, schema discovery, full-snapshot and cursor-incremental sync), credentials exclusively in Secrets Manager, cron or manual scheduling, per-connection error isolation in the worker, schema-drift detection and sync health on top.

A platform whose whole pitch is "connect your data" isn't credible to a real prospect on one source type. This pillar's build-out is mostly about breadth and resilience, not new concepts — the sync/credential/scheduling architecture already generalises, it just hasn't been asked to yet.

1. ~~**Generalise the connector registry before adding the second type.**~~ **Done — `STATUS.md` §21.** The interface is `validate_config`/`test`/`discover`/`snapshot`/`max_cursor_value` behind a `SourceConnector` Protocol, with the registry dispatching on `source_type`. Two shape notes for whoever adds the third connector: `snapshot()` and `incremental(cursor)` landed as one method (an incremental pull is the same extract plus a cursor predicate), and the byte cap is a caller-supplied parameter rather than a connector constant. The worker carries its own trimmed mirror of the extract half — see the standing note in `STATUS.md`'s rough edges about keeping the two registries in step.
2. ~~**MySQL/MariaDB connector.**~~ **Done — `STATUS.md` §21.** PyMySQL, tested end to end against a real MariaDB. It did its job as the abstraction's proof: it forced schema-vs-database vocabulary, per-dialect identifier rules, client-side CSV streaming (no server-side COPY), and code-keyed error translation to move into the connector rather than being assumed platform-wide. It also surfaced that `ssl_mode: required` needed real post-connect verification, since PyMySQL will silently finish a handshake in plaintext.
3. ~~**Object-storage file connector (S3/compatible).**~~ **Done — `STATUS.md` §22.** Bucket + prefix, discovery lists matching files with columns inferred through the datasets layer's own DuckDB readers, one object syncs as one dataset, and "incremental" means the object was rewritten (its `LastModified` is the cursor) since an object store has no row-level cursor. The roadmap's estimate that this was "a smaller lift than a new database driver" held for the ingest half but not the interface: being the first non-relational source, it forced `snapshot()` to return a file *plus its format* rather than always CSV — a Parquet object routed through CSV would discard the types it already carries. Unioning a whole prefix into one dataset is the natural follow-up and was deliberately left out; it needs a rule for what happens when two files under a prefix disagree on schema, which is a design question rather than an extra loop.
4. **A cloud warehouse connector** (Snowflake or BigQuery — pick whichever a real prospect conversation actually names first; don't build both speculatively). Same relational shape as Postgres/MySQL again, but credential handling differs (key-pair auth for Snowflake, service-account JSON for BigQuery) — first connector to exercise a non-password credential shape in Secrets Manager.
5. ~~**Generic REST/API connector.**~~ **Done — `STATUS.md` §24.** Scoped narrowly as this item asked: GET only, a dotted `records_path` to the array, two pagination styles (page number and echoed cursor), and all three named auth schemes. What it does *not* do is written into the connector so the boundary is visible — no Link-header pagination, no XML, no writes, and no server-side incrementality (there is no universal "changed since" for REST, so every run fetches the collection and incremental mode merges by primary key rather than saving bandwidth). Records land as JSONL, not CSV, so nested objects survive.
6. ~~**Schema drift detection.**~~ **Done — `STATUS.md` §23.** `sync_runs.schema_changes` (migration 0018), written by both the API's inline sync and the worker's scheduled job. One deviation from the plan above, with reasons recorded in the migration: the comparison is against the *previous dataset version's* schema, not a setup-time baseline — nothing records a schema at setup today, adding it would mean a discovery round trip per sync (for object storage, listing and downloading files just to read headers), and a stored baseline goes stale the moment anyone edits the connection. The trade is that drift is reported one sync after it happens and reflects what landed rather than what the source declares.
7. ~~**Sync health surfaced in the product.**~~ **Done — `STATUS.md` §23.** A `GET .../connections/sync-health` aggregate (one request for the whole page, not one per row) feeding a "Sync health" column — last result and when, success rate over the last 20 runs, last duration and row count, next scheduled run, and a drift badge — plus a per-connection History dialog with the full run list and expandable schema-change detail.
8. **Write-back connector (PostgreSQL first).** Actions today (§12) write back only to this platform's own dataset copy. Extend the PostgreSQL connector specifically to support a write path (an explicit opt-in per connection, scoped to specific tables/columns, audited the same way `action_runs` already is) — this is real new scope (conflict resolution: what happens if the source row changed since the last sync; permissions: who can enable write-back on a connection at all) and deserves its own design note before implementation starts, not just an extra method on the connector interface.
9. **Streaming sources (Kafka/Kinesis)** — explicitly a stretch item, likely not worth building until a real customer conversation names a concrete streaming need; the existing batch sync (full-snapshot + cursor-incremental) covers the overwhelming majority of "connect a data source" requests a Foundry-shaped product actually gets.

## 2. Datasets

**Current state** (`STATUS.md` §7, §25, §26): upload (CSV/TSV/Parquet/JSON/JSONL → canonical Parquet via DuckDB), preview, column profiling, data-quality expectations with a health badge, sandboxed arbitrary SQL query, export (CSV/Parquet), linear versioning.

The storage/versioning core is solid; what's missing is everything Foundry users actually mean by "Data Health" and richer lineage — the observability and trust layer on top of a dataset, not the storage mechanics themselves.

1. ~~**Column-level profiling in preview.**~~ **Done — `STATUS.md` §25.** `dataset_versions.column_profile` (migration 0019) plus a `Columns` tab beside the row grid. One deviation, argued in the migration: computed *lazily on first request* rather than at version-creation time. That still satisfies "once per version and cached" — a version's data is immutable, so the answer is valid forever and never needs invalidating — while avoiding an aggregate pass on every path that creates a version (upload, both sync paths, both model paths, action write-back) to produce something nobody may look at.
2. ~~**Data quality / expectations.**~~ **Done — `STATUS.md` §26.** All five rule types, per-column, with `error`/`warn` severity, and a pass/warn/fail/none health badge. One deviation, argued at length in migration 0020: results are computed **on demand and cached**, not at version-creation time. The seven creation paths across two codebases are a large blast radius, and — the real reason — a result computed at creation is stale the moment somebody edits the rules, which is exactly when a health badge most needs to be right. Any rule change invalidates the cache, and one read path computes-if-absent, so every creation path stays untouched and correct. The one thing this cannot do is alert at the moment a bad version lands (no reader to trigger the computation); that would need genuine eager evaluation and is flagged in the migration. Models' build-gating item can now read `GET .../datasets/{id}/health`.
3. ~~**Schema enforcement policy per dataset.**~~ **Done — `STATUS.md` §31.** `datasets.schema_policy` (migration 0023), `permissive` by default for the same reason 0022's gate defaults to `ignore`. One deliberate narrowing of "must match the previous version's schema": **adding a column is allowed under strict**. Taking it literally would reject the most common and most harmless drift there is, and a policy people keep switching off is one nobody leaves on — what breaks a downstream reader is a column going away or changing type. This item's recommendation that strict be the *default* for anything with a downstream dependency is deliberately not implemented: nothing should silently start failing pipelines on migration day, and "has a downstream model" is a property that changes without the dataset's owner doing anything. Enforced in a **trigger**, which is a reversal of migration 0021's argument against database logic and is argued at length in 0023 — the deciding factor is that seven writers across two codebases insert versions, so an application-layer check holds only until somebody forgets.
4. **Wire the Athena path that's already promised in code.** Upload/sync/model size caps (50MB/200MB/5M rows) are commented in code as "the point where the Athena/worker path takes over," but nothing calls Athena anywhere despite `workerTaskRole` already holding the IAM permissions for it (`infra/cdk/src/constructs/services.ts`). Either build the large-dataset path for real (a worker job that runs the same transform via Athena against data staged in S3, for datasets over the interactive cap) or remove the promise from the comments and the unused IAM grant — don't leave a customer's oversized upload hitting an opaque rejection with no real path forward.
5. ~~**Interactive lineage graph.**~~ **Done — `STATUS.md` §33.** The item said to reuse "whatever graph-rendering approach Models item 2 settles on"; reusing the same **endpoint** turned out to be the stronger version of that — `GET .../pipeline?focus=dataset:<id>` returns the node's connected component, laid out by the same code, and one React component renders both views. It also turned out this was as much "surface lineage at all" as "make it interactive": the Mermaid endpoint existed, was tested, and **nothing in the frontend had ever called it**. The component walk is deliberately *undirected* — a dataset's lineage is what produced it and what reads it, including a sibling model on the same input, which is what someone tracing an outage needs. The Mermaid endpoint stays for the spec's "exportable as JSON or Mermaid".
6. ~~**Dataset forking (lightweight branching).**~~ **Done — `STATUS.md` §34.** Exactly the small version this item scoped: `POST .../datasets/{id}/fork` copies one version into a new dataset with `origin='fork'` and provenance columns (migration 0025). Nothing here knows how to merge a fork back, on purpose — deciding what a merge means for tabular data is the large lift the item warns about, and it stays unbuilt until real usage shows forking is not enough. Three decisions worth carrying forward: the **bytes are copied, not shared** (sharing a storage key would make deleting the original silently empty the fork); the **quality rules travel but their results do not** (forking is for testing a change against the same standard, but a result is per-version and the fork's v1 is new); and a fork **starts permissive** whatever the source's schema policy was, since inheriting strict would make the thing you forked in order to experiment with refuse the experiment. It also got more useful than it looked when written: items 2 and 3 plus Models 3 are all things you want on in production, and all of them mean you now need somewhere else to try the change that would trip them.
7. **Export to a connection**, symmetric with Connections item 8's write-back — once a connection can accept writes, "export this dataset back to source" becomes a natural Datasets-side feature reusing the same path.

## 3. Models

**Current state** (`STATUS.md` §9, §14): SQL (DuckDB sandbox, synchronous) and Python (subprocess sandbox, worker-queued) transforms, manual/cron scheduling, run history, per-model lineage.

Foundry's Pipeline Builder is essentially this layer plus a real DAG view, real incremental builds, and quality gates — the conceptual pieces (models, datasets, versions, runs) already all exist here.

1. ~~**Upstream trigger mode.**~~ **Done — `STATUS.md` §27.** Exactly the pattern this item asked for: `list_due_upstream_models()` (migration 0021) discovers across workspaces, the worker re-verifies through a scoped connection, and due-ness is "an input dataset gained a version since `models.upstream_watermark`" rather than a cron tick. Two things the item didn't anticipate, both argued in the migration: a **self-loop guard** is required — a model whose output is also one of its inputs would otherwise re-trigger forever — and the **two-model cycle** (A→B→A) is documented rather than solved, because detecting it needs the whole graph, not one model's inputs, so it belongs with item 2. Chains settle one poll pass per link, which is a property of polling, not a bug; resolving a chain in a single pass needs topological order, again item 2's graph.
2. ~~**A real pipeline DAG view.**~~ **Done — `STATUS.md` §28.** A project-level `Pipeline` page: every dataset and model as one graph, last-run status and health on each node, pan/zoom, click a node for its detail and a jump to its own page. The item said to "build it on the same graph-rendering choice as Datasets item 5" — that choice turned out to be **no library at all**. The API returns each node's layer and position (`GET .../pipeline`, `services/pipeline.py`), so drawing it is arithmetic plus SVG beziers; that keeps the layering testable in pytest against real rows rather than only in a browser, and Datasets item 5 can reuse the same endpoint's shape for a single-node view. It also picked up the **cycle detection** that migration 0021 deferred here: cycles are grouped, reported, and drawn in the danger colour with a banner naming the consequence. Detecting a cycle is not preventing one — refusing to *save* an edge that closes a loop is a separate decision about model edits and is item 7 below.
3. ~~**Data quality gating.**~~ **Done — `STATUS.md` §29.** `models.input_health_policy` (migration 0022) with the three modes this item implies plus one it didn't name: `ignore` (the default, deliberately — applying a migration must not silently start failing models that ran fine yesterday), `warn` (run and record what was wrong), and `block` (refuse). `warn` earned its place: it is the mode you turn on to learn how often blocking *would* have fired, before committing to it. The gate holds on both the interactive API path and every automated one, which required mirroring the expectations evaluator into the worker — a gate that only held where a human was watching would be the same do-nothing promise item 1 existed to remove. It also, incidentally, supplies the "reader" migration 0020 said expectations were missing: the gate computes health when nothing has cached it, so `block` is enforced against data nobody has opened.
4. **Incremental model builds.** Today a model run appears to fully recompute from its inputs' current state every time. For SQL models over a connection-backed dataset that's itself grown large, add an incremental mode mirroring Connections' cursor-incremental sync (process only rows new since the last successful run, keyed on a declared cursor column) — matters for real performance parity once datasets aren't toy-sized.
5. ~~**Model version history / rollback.**~~ **Done — `STATUS.md` §32.** `model_versions` (migration 0024), same append-only shape as dataset versioning, backfilled so every existing model starts at v1. Three decisions the item didn't specify. **Rollback appends rather than rewinds**: restoring v2 writes a new v5 with v2's content, so history stays a true record and `model_runs.model_version` never becomes ambiguous. **A version snapshots the code *and* the inputs**, because aliases are half the contract — restoring `FROM orders` into a model whose input was renamed restores something that cannot run. **Trigger mode, schedule, health policy, name and description are not definition changes**: they are how and when a model runs, not what it computes, and versioning them would fill the history with entries nobody would roll back to. It also closes the asymmetry that motivated the item: `model_runs.output_version` has always pointed at the exact data a run produced, and `model_version` now points at the exact code. A side-by-side diff view is deliberately not built — the versions are stored, so it can be added later without a schema change.
6. **Dependency-aware scheduling.** Once item 1 (upstream triggers) exists for the common case, this becomes mostly moot for chained pipelines — but independent cron-scheduled models with an implicit ordering expectation (B should run sometime after A's daily sync, but isn't literally fed by A) still race today. Lower priority than items 1–5; revisit once upstream triggering is live and it's clear whether this gap still matters in practice. **Now revisitable:** item 1 is live, and the gap it leaves is narrower than written here — a model that is genuinely fed by another needs no scheduling at all now, so what remains is only the implicit-ordering case, plus the one-pass-per-link settling time, which is a latency question rather than a correctness one.
7. ~~**Refuse to save a model edit that closes a cycle.**~~ **Done — `STATUS.md` §30.** In `_validate_and_set_inputs` as this item proposed, via a recursive walk over every dataset downstream of the model's own output. Existing cycles are **grandfathered**, which is the question this item left open: the check validates the *proposed* input set, so a pre-existing loop keeps working until somebody edits one of its models, at which point the edit is refused until they break it. Force-breaking on next edit would mean silently deleting an input someone configured on purpose — the Pipeline page names the loop instead, which is a better place to be told.

## 4. Objects (Ontology)

**Current state** (`STATUS.md` §10, §11, §12, §14, §35): object types + typed properties + link types (workspace-scoped), dataset→type mappings with sync (project-scoped), an instance store behind a Protocol with Postgres and OpenSearch implementations and a backfill between them (§35), Actions for write-back to the platform's own dataset copy.

The structural gap that used to head this section is closed, item 2 cashed it in, item 3 made the ontology *connected* rather than merely typed, item 5 made it *editable* — which it had never been — and item 4 made its types *mean something*, which they had never done either. Only item 6 remains, and the item itself asks to wait for production usage of single-instance actions before designing bulk ones. **Canvas is where the next startable work is**: its item 3 has since cashed in this pillar's Explorer and property-type work in a canvas widget, and item 4's geopoint has cleared the way for the map widget there.

1. ~~**Cut the instance store over to OpenSearch.**~~ **Done — `STATUS.md` §35.** All four things this item asked for, plus two it could not have known about. The seam is `PostgresInstanceStore` implementing the *same* Protocol as the OpenSearch one, so the Postgres path stays as the fallback and local-dev default instead of being deleted at cutover; `backfill()` is the migration step, and it is **idempotent**, which is what let the dual-write period be replaced by a simpler procedure (**backfill, flip, backfill again**) rather than machinery that fails quietly when one of two writes does. Every existing objects/actions test passes through the seam unchanged, and the whole instance API is additionally tested end to end *on* the OpenSearch store. The two surprises: `action_runs.instance_id` had a foreign key into `object_instances`, which is unsatisfiable once instances live elsewhere (migration 0026 drops it), and **`opensearch-py` alone does not provide `AsyncOpenSearch`** — it needs the `[async]` extra, so the gateway §14 shipped would have raised ImportError the first time a deployment used it. Remaining honestly unverified: no real cluster. The gateway is tested over real HTTP against a fixture implementing the REST subset it uses, which proves its requests and parsing, not that OpenSearch agrees.
2. ~~**Global Ontology / Object Explorer.**~~ **Done — `STATUS.md` §36.** `GET .../object-instances?q=&type_id=` searches every instance in a workspace at once, and the objects page gains an Explore panel over it: one table, one row per instance, each labelled with the type it is, with a union of the properties present so a cross-type result still shows values rather than ids. Two things worth carrying: it is **workspace-scoped, not project-scoped**, because object types are — an explorer that stopped at a project boundary would show a partial ontology and call it the whole one; and `search()` is on the *Protocol*, so the Postgres store implements it too, honestly, as `ILIKE` over the properties JSON. That is substring matching, not search — no tokenisation, no relevance — which is exactly why this item was sequenced after the cutover, and it is written into `services/instances.py` rather than left to be discovered.
3. ~~**Relationship/link traversal UI.**~~ **Done — `STATUS.md` §37.** The item described a UI, and the UI is there — an Explore panel on any instance, one section per link, with click-through and a breadcrumb trail. But it was **not a UI item**: `link_types` recorded only *which types* relate, and `grep` found no link-instance table anywhere in twenty-six migrations, so there were no edges between instances to browse. The decision that had to be made first was where instance-level links come from, and the answer is **derived, not stored**: migration 0027 adds `from_property`/`to_property` to `link_types` and a traversal joins on those values. Instances are themselves *materialised* from dataset mappings and re-materialised on every sync, and the relationship already arrives in that data as a foreign key column — storing edge rows would have meant a second sync mechanism going stale beside the one that produces the rows its edges point at. Two things the item did not anticipate: `'$primary_key'` had to be a reserved join reference, because the far end of a foreign key is nearly always the referenced row's key and the primary key is a field on an instance rather than one of its properties; and the join needed an **exact-equality** store operation, because the only lookup that existed was the Explorer's `phrase_prefix` search, which would have answered "who works in ENG" with the people in "ENG West" and no visible sign of the error.
4. ~~**Richer property types.**~~ **Done — `STATUS.md` §39.** The item guessed "today's typed properties are presumably basic scalars". Wrong in a more useful way than it is right: **`geopoint` and `timestamp` have been in the enum since migration 0003 as labels nothing enforced.** `actions._validate_value` checked integer/float/boolean/string and silently accepted anything at all for date, timestamp, geopoint and json, so a property declared `geopoint` took the string "banana"; the sync path wrote whatever the mapped column held without ever consulting the declared type. So the work was not "add types", it was "make three existing types mean something and add the one genuinely missing". Both write paths now share one `coerce_property_value` — a type enforced on one path and not the other is not a type — which is also why this had to become the codebase's *fifth* mirrored file, with a byte-parity test and the debt written up rather than hidden. On the item's own sub-questions: timestamp **was** indistinguishable from a plain string and now parses as ISO-8601 with an offset preserved when present, but it deliberately did *not* split into `timestamp`/`timestamptz` — the values come from CSV and Parquet columns whose own timezone awareness varies by file, so that type would promise what the ingest path cannot keep. Attachments point at the existing storage gateway exactly as asked, and forced two design findings the item could not have known: an attachment property **must be mapped to a dataset column** like any other (instances are re-materialised from their dataset, so an ontology-only value would be deleted by the next sync), and write-back therefore stores the *whole* reference as JSON in that column rather than just the key, or the filename, content type and size would degrade on every sync. geopoint renders as coordinates rather than a map: a map needs a tile source, which is an outbound request from a page showing a customer's own data, and that decision belongs in the Canvas map widget this item unblocks — made once, not smuggled into a table cell.
5. ~~**Ontology change history.**~~ **Done — `STATUS.md` §38.** The item said changing an object type has "no audit/version trail today". True, and understated in the same way item 3 was: **there was no way to change one at all.** `create_type` and `delete_type` were the entire surface, and delete cascades — properties, dataset mappings, link types, actions and every materialised instance go with it — so "rename a property" meant destroying the ontology around it and rebuilding by hand. Versioning a change that cannot be made is not a feature, so this shipped as a pair: `PATCH .../object-types/{id}` (a whole-definition replacement, since impact is a property of the whole change) and migration 0028's append-only `object_type_versions`, restore-appends-rather-than-rewinds exactly as Models item 5 does one layer up. The part the item got most right is the warning, and the reason is worth keeping: **no consumer of a removed property raises anything.** A dataset mapping keeps writing the property on every sync while the browse UI, which reads the *declared* properties, stops showing it — the data keeps arriving and becomes invisible. An action's value check falls back to `property_types.get(prop, "string")`, so a removed integer property silently starts accepting any string. A link join whose property is gone traverses to nothing forever, indistinguishable from data that genuinely has no matches. There is no exception anywhere to catch, which is the entire argument for refusing the edit until somebody acknowledges it rather than logging a warning nobody reads. One deviation from the item's list of consumers: Canvas apps are *not* checked, because a widget references a dataset or an action rather than a property directly, so the action check already covers the reachable case — stated in STATUS rather than quietly skipped.
6. **Richer Actions.** Today's actions write back to exactly one instance. Bulk/multi-object actions (apply the same write across a filtered set of instances) and action side-effect chaining (an action that also, say, triggers a model run) are natural extensions of the existing `action_types`/`action_runs` shape — scope as a follow-up once single-instance actions have real production usage to learn from, not before.

## 5. Canvas

**Current state** (`STATUS.md` §15): Craft.js-based visual editor, four widgets (Container, Text, Dataset table, Action form), publish visibility (private/workspace/groups).

The "BI" half of "app/BI builder" is the explicit, named gap here (STATUS.md's own words) — this pillar's build-out is mostly about closing that. Items 1–4 and 6 are done, which closes the named gap and then some: there are charts, they react to shared parameters, a canvas app can read the *ontology* rather than only raw datasets, geopoints are on a map, and a published app is finally something a workspace member can open. **What is left is item 5** (a deferred design question whose commonest case parameters already cover) **and item 7** (an explicit stretch needing an auth model for viewers outside the platform) — so the next substantial work is **Code**, the one pillar with no scaffolding at all.

1. ~~**Parameter/filter widgets.**~~ **Done — `STATUS.md` §40.** Exactly as the item sequenced it: the mechanism first, so charts and cross-widget interactivity have something to subscribe to. `CanvasParameterProvider` is a **second context** rather than an extension of `CanvasEnv`, which the item suggested — parameter values change on every keystroke while `CanvasEnv` changes only when the app remounts, and merging them would re-render every widget that only wanted to know which workspace it is in. The values are runtime state and deliberately *not* saved with the app: a parameter's name, label and options are node props, but the value a viewer has selected belongs to this render, so a published app opens at its defaults for everyone rather than at whatever the last person chose. Two decisions worth carrying forward: a dropdown's options come from **the column's distinct values, not a list typed by the builder** (a hand-typed list is a copy of the data that goes stale the first time a new value appears — the same argument that made object links derived in Objects item 3); and filtering is **server-side**, because filtering the preview page in the browser would silently filter the first 50 rows while appearing to filter the dataset. The date-range control the item named is not built — `select` and `text` are, and a range needs a two-value parameter shape that should be designed against a real chart's needs rather than guessed at now.
2. ~~**Chart/BI widgets.**~~ **Done — `STATUS.md` §41.** All four kinds, bound to a dataset and reactive to item 1's filter parameters. Two deviations from the item, both deliberate. First, it offered "aggregated client-side for small results or via a new lightweight aggregation endpoint for larger ones"; **neither was taken** — aggregation is always server-side through the *existing* query endpoint's `GROUP BY`, because there is no reliable way for a widget to know a result is small before fetching it, and a chart that sums the preview page and puts an axis on it does not show less data, it shows a **wrong number** that looks authoritative. No new endpoint was needed, and going through the existing one inherits its sandboxing (`enable_external_access=false`, memory limit, row cap) for free. Second, **no charting library**: the four shapes are a few dozen lines of SVG each, and the same call was already made for the pipeline graph (§28, server-side layering so the web app needs no graph library). `charts.tsx` says where that trade flips — tooltips, zoom, brushing and stacked series are the point to reach for a library rather than grow a bad one. Details worth carrying: bar and pie sort by value and cap the categories while line sorts by its dimension (a line sorted by magnitude draws a shape that means nothing); scatter does not aggregate at all, since grouping destroys the thing being looked at; a non-numeric measure fails with DuckDB's own message rather than summing to null and drawing an empty chart that reads as "no data"; and the zero baseline is always included, since a bar chart whose baseline is not zero is the commonest way a chart lies.
3. ~~**An Ontology Object browser widget.**~~ **Done — `STATUS.md` §42.** The item's sequencing was right — Objects item 2's Explorer is exactly the surface to reuse — but reusing it was not enough, and the gap is the interesting part. **The Explorer only ever asked one question**: `q`, a prefix search across every property of every type. That is the right question for a search box and the wrong one for a *filter*: a dropdown bound to `name` that quietly also matches `Depot North` when the builder chose `Depot` is not filtering, it is searching with a filter's UI, and nothing about the result looks wrong. So the endpoint gained an exact read path — backed by the `find_by_property` the store Protocol already had from Objects item 3, where a link join is precisely "instances whose property equals this value". Three constraints fell out of the endpoint rather than the widget: an exact filter **requires exactly one type** (a property api_name only means something within a type — `name` on `Site` and `name` on `Customer` are different properties that share a spelling); `property` and `value` are refused unless **both** are present, since a `property` with no `value` degrading to "unfiltered" is the same quiet wrongness the filter exists to prevent; and `$primary_key` is filterable through Objects item 3's sentinel. In the widget, exact filter and free-text search are **separate settings, not blended** — the header states which is in force, so a viewer can see the question and not just the answer. Values render through Objects item 4's shared `PropertyValue`, so a geopoint reads as coordinates and an attachment as a download link inside a canvas app too: a type that means something on the browse page and `[object Object]` in an app does not mean anything.
4. ~~**Map widget.**~~ **Done — `STATUS.md` §43.** Its dependency (Objects item 4's geopoint) shipped, and so did the question that item deferred here: **where the basemap comes from**. The answer is no tiles at all. Every mapping library defaults to raster tiles from a third-party host, and that default is wrong for this product specifically — Anchor deploys into the customer's own AWS account, often into a VPC with no egress, and a tile layer makes the *viewer's browser* call out to somebody else's server on every pan, carrying a viewport that approximates where the customer's data is. So the basemap is Natural Earth's 1:110m outlines, simplified to a ~60 KB path in the bundle, regenerable by a script that ships with it. The cost is real and is stated on screen rather than buried: there is no street-level detail, so the widget says "country outlines only" past a few degrees of zoom, and the *fitted* view has a ten-degree floor so it never opens on a meaningless polygon. A configurable tile URL pointing at a host the customer chose is the named extension point, not a half-built option. No mapping library either, for the same reason item 2 took no charting library — with tiles gone, what is left is an affine transform, a drag handler and a grid clustering pass. Both sources the item named are bound through **one** parser, `toLatLon`, whose accepted shapes are the API's: Objects item 4 made a synced geopoint arrive in a dataset column as `"lat,lon"`, so a widget that understood only the ontology's shape would fail against the datasets its own objects came from. The rest of the design is refusals: an unreadable location is counted rather than dropped, an out-of-range coordinate is rejected rather than clamped (the usual cause is lon/lat the wrong way round, and clamping draws that confidently at the edge of the world), points panned off the edge are counted, and rows beyond the explorer's page cap are reported instead of the cap being raised platform-wide to suit one widget.
5. **Cross-widget interactivity beyond filters** — e.g. a table row selection driving another widget's detail view — same resolver/widget extension pattern as the rest of this pillar, lower priority than items 1–4 since parameter widgets (item 1) already cover the most common real use case.
6. ~~**Drag-and-drop reordering of placed widgets**, published-apps nav page.~~ **Done — `STATUS.md` §44.** The item called itself polish — "the read API already exists — just needs a list page and a nav entry" — and the list page was indeed the easy half. The other half is that **publishing had nowhere to lead**: the only route that rendered an app was the project editor, which resolves its project by slug and reads the project-scoped endpoint, so anybody without project membership — the exact audience publishing exists for — followed a link to an app published to them and got a 404. So this shipped as a gallery *and* a viewer route, workspace-scoped, with the editor hard-disabled rather than merely chrome-hidden. The gallery is deliberately not a project tab: somebody who opens a dashboard every Monday should not have to learn the builder's filing system. Building the viewer also made an existing claim testable and an existing one wrong: publishing shares **the layout, not access to the data** (every widget still reads as whoever is looking, which is what stops an app becoming a way to launder access — now pinned by a test rather than left as an assumption), and the Publish dialog's "shares the current saved version" implied a pinned snapshot when publishing is a visibility flag over the live definition. Reordering got **two buttons as well as drag**, for the same reason the roadmap's own rough edges note: native HTML5 drag is the one canvas interaction automation cannot drive, and it is also the one a keyboard cannot do at all.
7. **Embedding/sharing outside the platform** (a public or token-scoped share link) — explicitly a stretch item; bigger scope (auth model for an unauthenticated or token-authenticated viewer) than anything else in this section, revisit once the widget set itself is actually competitive.

## 6. Code

**Current state** (`STATUS.md` §45–§47): all four items done. The decision is made (no git server; the system of record stays in Postgres), the surface exists — file tree, source, computed diffs and a commit log over the project's transforms, with change sets grouping one edit across several of them — and code changes can be gated behind review, per project. What is left in this pillar is optional and named rather than assumed: the git *mirror* to a remote the customer owns, and branch-to-environment mapping, which item 4 declined for a stated reason rather than skipping.

Foundry's real Code Repositories are git-backed and tightly coupled to the pipeline layer (checked-in transform code building datasets via CI, with review-gated promotion). Because nothing exists yet and this platform's whole premise is running entirely inside the customer's own AWS account (not phoning home to an external git host), this pillar needs a short design spike *before* implementation — unlike the other five sections, don't start writing code for item 2+ until item 1 is actually decided. **Item 1 is now decided** (`docs/decisions/0001-where-code-lives.md`), and it changed the shape of the rest as it warned it would: item 2 becomes a surface over `model_versions` rather than a new backend, item 3 stops being a round trip at all (there is no second copy to round-trip with), and item 4's approval must be platform-native because an external repository must never be what authorises a change to what runs here.

1. ~~**Design spike: where does the git data live?**~~ **Decided — `docs/decisions/0001-where-code-lives.md`.** The answer is neither option as posed: **do not build a git server, and keep the system of record in Postgres**, with git federation available later as an optional outbound mirror to a remote the customer already owns. The argument the item could not have made is that the choice was already constrained: `model_runs.model_version` pins each run to the exact definition that produced it, and migration 0024 makes rollback append rather than rewind specifically so that pointer resolves to one piece of code forever. A git ref does not have that property — branches move, history can be rewritten, a commit reachable today can be gone after a force-push — so git cannot *be* the store without either accepting runs that point at code which no longer exists or rebuilding immutability on top of it. That settles the rest: a self-hosted server becomes a second copy of the same code whose only remaining value is developer tooling interop, which a private-subnet server cannot deliver anyway (no public ingress, no EFS, ephemeral Fargate tasks), while federation to *the customer's own* GitHub is the same category of thing the Connections pillar already does — an outbound connection over egress the VPC has, with the credential in the existing `SecretsGateway`. What the pitch protects is that the vendor holds no customer data, not that the customer may not use their own SaaS.
2. ~~**Scope narrowly: transform code first, not a general IDE.**~~ **Done — `STATUS.md` §46.** The narrow scope was right and item 1 made it narrower still: "a git-backed store for Model definitions" is not what got built, because the store already existed. What shipped is the repository-shaped *surface* — file tree, source, computed diffs, commit log — plus migration 0030's **change set**, the one thing the schema genuinely could not say (a save has always written one version row per model, so an edit spanning three transforms was three unrelated events). Membership is nullable and stays that way: versions written before 0030, and every save from the inline Models editor, have no change set, and backfilling a synthetic one would invent an intention nobody expressed. So the log has two kinds of entry — a grouped edit with a message, and a standalone save — which is the truth about how the code gets edited rather than a smoothed-over version of it. Every write goes through `models.update`, so a change set cannot bypass a check the inline editor enforces (a test drives cycle refusal through one and asserts the whole thing rolls back), and a change set in which nothing actually changed is refused rather than recorded. Two details worth keeping: a path collision suffixes *both* sides, since otherwise one model's path would move when an unrelated model was renamed; and diffs are computed on read, which surfaced a real bug — `unified_diff` with `keepends=True` runs the last `-` line into the first `+` line when the source has no trailing newline, invisible in API tests and obvious in a browser.
3. ~~**Round-trip with Models.**~~ **Done by construction — `STATUS.md` §46.** There is no round trip to build: editing through Code calls the same `models.update` the inline editor calls, so the build path follows automatically and the versions written are the same rows a run resolves against. Kept below for the reasoning, which item 1 confirmed rather than replaced. Editing a Model's code through Code should trigger the same build path (`model_runs`/`dataset_versions`) the existing inline editor already produces — Code becomes an alternate, version-controlled *authoring surface* for the same underlying pipeline concept from Models item 5, not a parallel, disconnected system. This also means Models item 5 (definition versioning) and Code's commit history may end up being the same mechanism viewed two ways — worth explicitly reconciling during item 1's design spike rather than building both independently and merging later. **Reconciled, and the answer is stronger than "may":** they are literally the same rows, so there is no round trip to get right — editing through Code calls the same service the inline editor does and therefore takes the same build path by construction.
4. ~~**Review-gated promotion.**~~ **Done — `STATUS.md` §47.** Two of the three pieces the item names got built (review UI, approval state); the third, **branch-to-environment mapping, was declined**, because this platform has neither branches nor environments and item 1 settled that it never will have a branch — `models.code` is live, and a run is pinned to the exact row that produced it. So "live" is the project, and the gate sits on the write that makes a definition live rather than on a merge between two refs. A proposal is a *request*: its files never enter `model_versions` (what a run resolves against must not hold unapproved code), and applying writes them through item 2's change set path so an approved change lands in the same log as every other edit. The gate lives in `models.update` rather than a route, because that function is what makes a definition live and the two authoring surfaces are two doors into it; it gates code and inputs only, so a gated project can still pause a job. Three ways round a review are refused and tested: approving your own proposal, approving-then-swapping the code (editing files invalidates prior approvals; editing the summary does not), and applying a proposal whose file somebody else has since changed — re-checked at *apply* time, since the gap between review and apply is where the lost update lives. Blockers are returned as a list of reasons rather than a boolean, because a disabled button with no explanation leaves somebody guessing which of four rules they tripped. **Item 1's constraint held**: approval state is platform-native, in Postgres against platform identities.

## 7. Deployment and onboarding

**Current state** (`STATUS.md` §17–§20, §48–§49): **all four items are done.** There is a hosted onboarding page, a control-plane HTTP surface and image behind it, an operator CLI that can finally provision as well as destroy, a runbook (`docs/deploying.md`), a first-run checklist in the product, and failures that explain themselves. A customer stack is a real, working CDK deployment — one command's worth of infrastructure, migrations that run themselves on every deploy, and a first-run `/setup` page that creates the organisation and its first owner. Everything *before* that page is a runbook, and part of it is not even that: the operator CLI can `deprovision` a customer but has **no `provision` command**, so creating a stack today means importing `Provisioner` in a Python REPL.

The product's pitch is that it runs in the customer's own AWS account. That pitch is only as good as the twenty minutes in which they connect that account — today those twenty minutes are: find a YAML in a repo, paste two parameters by hand, email a role ARN to the vendor, wait fifteen silent minutes, and be told a URL. Every step of that is somebody's chance to bounce.

Ordered by leverage, not by size:

1. ~~**Operator ergonomics: a `provision` command, the vendor bootstrap, and the runbook.**~~ **Done — `STATUS.md` §49, §50.** `onboard`, `provision`, `status`, `serve` and `demo`, all over §48's service so the CLI and the page refuse identically. Two things the item did not list and should have: the control plane had **no Dockerfile at all** — it never needed one until it grew a web surface, and its image has to carry Node, the CDK CLI and `infra/cdk`, because `cdk deploy` is a subprocess. A third thing the item missed entirely, added in §50: the customer's path was one page while **the vendor's path to make that page exist was still five manual steps** — a KMS key, a role with the right trust policy, three ECR repositories, a hosted template, and working out which variable wants which ARN. `cli init` is those five, idempotently, ending in the exact environment block; it stops at the registry database and where the page is hosted, and says so, because both are decisions with a bill attached. And `docs/deploying.md` is written as **three test levels** rather than a command list: the whole flow with no AWS (`cli demo`, which scripts an account that starts un-assumable so the failure screens can be walked for free), one stack by hand, then the real thing through the page — including which calls level 3 exercises for the first time. `cli onboard --org-slug` registers the customer and prints a **prefilled CloudFormation launch URL** (external ID and control-plane role ARN already in the query string), so the customer's job is click → tick the IAM box → Create. `cli provision --org-slug --account-id --region` *derives* the bootstrap role ARN rather than asking for it — the template hardcodes `RoleName: platform-bootstrap`, so account ID plus region is enough and the ARN paste is pure ceremony — then runs preflight, deploys while streaming CloudFormation events, and prints the app URL and its `/setup` link. `cli status --org-slug` shows registry state plus live stack events. Also: `docs/deploying.md`, the runbook that does not exist, including the `docker build --platform=linux/amd64` rule this build has been bitten by twice (`STATUS.md` §20).
2. ~~**Self-service onboarding: a control-plane HTTP surface and a hosted onboarding page.**~~ **Done — `STATUS.md` §48.** The structural gap is that there is no surface the customer can touch at all — `apps/web` runs *inside* the stack being provisioned and has no path to the control plane's trust boundary (§19). One page, five steps: connect your AWS account → launch the bootstrap stack from a button → the control plane detects the role appearing (poll `sts:AssumeRole` against the derived ARN; no paste of anything but a 12-digit account ID) → preflight results in plain English → live provisioning progress from CloudFormation events → hand off to `/setup` in the new deployment. Authenticated by a per-customer onboarding token, since by definition the customer has no account in a platform that does not exist yet. This subsumed most of item 1's machinery as predicted: the launch URL, the derived role ARN, preflight and the event stream are all service functions now, so **what is left of item 1 is a thin CLI over them** plus `docs/deploying.md`. Two things the item did not anticipate. The customer types **twelve digits and nothing else** — the bootstrap template hardcodes the role name, so the ARN that used to travel by email was ceremony, and ceremony is where typos live. And the external ID is returned by *no* route, not even the operator one that creates the onboarding: once the launch link is minted server-side, handing the plaintext back is a secret with no caller.
3. ~~**Guide the first ten minutes inside the product.**~~ **Done — `STATUS.md` §49.** A checklist on the project overview, every item **derived** from what exists rather than ticked by hand, retiring itself when all four are done. The bug worth remembering: the ontology step first counted `resource_counts.objects`, which is **workspace-wide**, so a brand-new project opened with it already ticked by somebody else's 26 object types — a green tick claiming work nobody had done. It counts the project's own object type *sources* now. Original text: `/setup` currently hands somebody a blank workspace with six pillars and no hint which door to open first. A first-run checklist (connect a source *or* upload a CSV → build a model → give it an object type → put it on a canvas), each item ticking itself when the thing exists, and optionally a one-click sample project. Cheap, and it is the difference between a deployment that gets used and one that gets forgotten.
4. ~~**Failure recovery as a product, not a runbook.**~~ **Done — `STATUS.md` §49.** Failures come back in plain English with the one action that fixes each, and a failed deploy offers a retry. The hints are the failures this build actually hit, including the nastiest one to read cold — a cancelled resource whose real cause is an *earlier* failure further down the events. An unrecognised failure gets no invented advice: CloudFormation's own reason beats a guess dressed as guidance. Original text: `STATUS.md` §17 and §20 document real traps — a `CREATE_FAILED` whose rollback sticks on RDS deletion protection, an OpenSearch domain CloudFormation never told to delete, images built for the wrong architecture. Today each one is a human reading a wall of stack events. Preflight prevents some; the rest want the onboarding page to say what failed, in plain English, with the one action that fixes it. Sequence after 2, since it needs the same event stream.
